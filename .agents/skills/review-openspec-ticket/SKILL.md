# Review OpenSpec Ticket

Review one ticket's implementation. Produce findings; do not edit code, tickets, or OpenSpec tasks. The implementing agent resolves findings and requests another review before marking the ticket done.

## 1. Resolve the ticket and its authority

- Select the change and the ticket named by the caller. If either is ambiguous, ask; never choose a ticket merely because it is first. Run `openspec status --change "<name>" --json` and `openspec instructions apply --change "<name>" --json` using the selected OpenSpec root or store. Use the returned `changeRoot` and `contextFiles`, not a presumed repository-relative path. Stop if the change is absent or its required planning artifacts are missing.
- Read the ticket under `<changeRoot>/tickets/`, all context files returned by the CLI, and any applicable repository policies and standards (if present). Check its `Covers OpenSpec tasks`, `Blocked by`, behavior-spec references, deliverable, and acceptance criteria against the current artifacts. A ticket cannot change OpenSpec behavior or override project policy; report a conflict before reviewing an assumed replacement contract.
- Obtain the implementer's changed-file inventory, observed test/smoke results, and the before/after comparison if one exists. Use a Git diff only when a real fixed point exists; include untracked/new files in scope. Without a fixed point, inspect the affected files and their callers directly and disclose the scope limitation. Do not attribute unrelated user edits to this ticket or claim an exhaustive diff you cannot establish. If the affected code cannot be identified, ask for the missing scope instead of inventing a review result.

## 2. Conduct two independent, read-only reviews

Use separate reviewers in parallel when available; otherwise make two separate passes and disclose that reviewer independence was unavailable. Give both reviewers the affected code and observed check results, but keep their judgments separate. Reviewers do not change files or rerun the implementer's checks.

**Standards reviewer:** Compare the code, tests, documentation, and changed interfaces with applicable documented repository standards (if any), actual project tooling/configuration, and relevant existing conventions. Identify concrete correctness, maintainability, security, and test-quality defects not already resolved by the reported tooling checks. For each new or materially changed permanent test, identify the distinct approved regression it detects at its chosen seam beyond existing tests and whether its assertions capture the approved outcome rather than incidental implementation details; report redundant or implementation-coupled tests without inventing new requirements. Cite the affected file and line, the governing rule when applicable, severity, and a minimal remedy. Do not flag a stylistic preference as a hard violation.

**Spec reviewer:** Read every OpenSpec capability spec affected by the ticket, not just the first one; use the ticket's task mapping and acceptance checks to bound this delivery. Compare user-visible behavior, error cases, reliability guarantees, and affected documentation against the approved requirements and scenarios. Identify missing or partial behavior, incorrect behavior, and unrequested behavior; cite both the spec requirement and the affected implementation when possible. Treat proposal and design as scope and approach context, not substitutes for a behavioral spec. If this change legitimately has no spec delta, say so and review only its approved non-behavioral scope; never report a behavioral Spec pass without a behavioral spec. A ticket referring to a missing spec is a blocker.

**YAGNI check (both axes):** For each added edge-case guarantee, defensive abstraction, or permanent test, identify its approved OpenSpec requirement or explicit repository quality rule. For defensive code, explain which required outcome would fail in a credible scenario without it; for tests, apply the Standards review's distinct-regression check. A test written for the edge case, a retrospective ticket explanation, or merely related broad wording does not establish authority. On Standards, cite untraced additions as scope violations and propose the smallest removal or simplification; on Spec, cite unrequested user-visible behavior as scope creep. If the claimed requirement is reasonably open to competing interpretations, report "scope decision needed" with both interpretations and the smallest compliant option for human approval, neither a pass nor a blocking defect. Reviewers must not promote a reviewer-constructed edge case to a blocker without that authority: present its credible trigger, user impact, simpler alternative, and implementation cost as an advisory for human decision before asking for handling or tests. A demonstrable breach of approved behavior remains blocking.

## 3. Report without closing the ticket

Report `## Standards` and `## Spec` separately. Within each axis, list evidence-backed blocking findings, advisory findings, scope decisions needed, and coverage limits; report an explicit pass only for the scope actually inspected and resolved. Finish with findings counts, unresolved scope decisions, and the worst severity per axis, not a blended score. State exactly which test and smoke evidence was supplied and which was not observed; this review does not manufacture verification.

Do not mark the ticket `done`, check an OpenSpec task, commit, sync specs, archive, or start another ticket. The implementing agent addresses blocking findings within the approved scope, reruns affected checks and actual behavior, and requests a fresh review of the changed areas. Before ticket closure, the implementer obtains a human decision on unresolved scope questions: approve a revision to the owning artifact or remove unapproved additions. Scope or spec changes require the project's human approval process before implementation continues.
